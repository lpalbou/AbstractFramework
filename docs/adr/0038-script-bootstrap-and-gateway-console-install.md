# ADR-0038: Script Bootstrap and Gateway Console as the Install Experience

## Status
Accepted (2026-09-23)

## Dates
- Proposed: 2026-09-23
- Accepted: 2026-09-23

## Context

`docs/installers/` described a two-tier plan: a cross-platform GUI "Installer Manager" with
separate notarized/signed builds per OS (`.dmg`/`.pkg`, `.msi`/`.exe`, AppImage/Flatpak) plus a
signed package per app. None of it shipped; the only prototype (the standalone
`AbstractInstallers` repository) is an unsigned macOS-only Tauri app. The plan made every user
benefit wait on Apple Developer ID and Windows EV code-signing pipelines for three OSes and many
apps.

Meanwhile the pieces the manager was meant to provide exist elsewhere:

- `uv` provisions Python 3.12 and installs a package as an isolated, user-scoped tool on macOS,
  Linux and Windows without admin rights, and `uv tool upgrade` updates it in place.
- The AbstractGateway web console (`/console`) already configures providers, API keys, defaults,
  users and model downloads, and the gateway's self-update recognises `uv tool` installs.
- Ollama, LM Studio and uv all ship their own one-line vendor installers (`curl | sh`,
  `irm | iex`), signed by their vendors where a binary is involved.
- A script fetched with `curl` carries no quarantine attribute on macOS, and `irm | iex` writes no
  file on Windows, so neither Gatekeeper nor SmartScreen gates a script bootstrap.

## Decision

1. **The install experience is a one-line script per OS plus the gateway's own console.**
   `scripts/install.sh` (macOS, Linux; POSIX `sh`) and `scripts/install.ps1` (Windows PowerShell
   5.1 and PowerShell 7) are the bootstrap. After the gateway starts, the browser opens `/console`,
   and the console (with its first-run wizard) is the guided UI. There is no separate GUI installer
   application. This supersedes the "Installer Manager" and "signed per-app package" plan in
   `docs/installers/`.
2. **uv is the runtime provisioner.** The bootstrap installs uv when missing, runs
   `uv python install 3.12`, and installs `abstractgateway[<profile>,tray]==<pin>` with
   `uv tool install --python 3.12`. It always passes `--python 3.12`. Node.js for the npx apps
   comes from the `nodejs-wheel` uv tool when no Node 18+ exists. Nothing in the default path
   needs admin rights.
3. **Pins come from the generated install manifest.** The scripts read
   `bootstrap.gateway_version` from `docs/installers/install-manifest.json` and embed the same
   value for `curl | sh` use; tests fail when they drift. The manifest is generated by
   `abstractframework manifest` from the root release pins (ADR-0034 release order).
4. **Every step has a CLI twin.** The scripts print each command they run, `--print`/`-Print`
   shows the full plan without changing anything, and the final summary lists the commands so a
   user can reproduce the install by hand. The scripts call the same commands the docs teach.
5. **The gateway owns service registration and sign-in.** The scripts delegate autostart to
   `abstractgateway service install` and the browser sign-in to
   `abstractgateway-config claim-url` when the installed gateway provides them, detected with
   `--help`. Otherwise the scripts start the gateway in the background (plus a Startup-folder
   shortcut on Windows) and point the user at the bootstrap admin token file. The scripts never
   write LaunchAgent plists or systemd units themselves.
6. **Loopback only.** The bootstrap binds the gateway to `127.0.0.1`. Remote access uses an SSH
   tunnel or the container deployment with explicit auth.
7. **Third-party engines are installed by their vendors' installers.** `--with-ollama` and
   `--with-lmstudio` run the official Ollama and LM Studio installers, announce any sudo/UAC
   prompt before running, and skip when the engine is already installed or reachable.
8. **Code signing is reserved for native double-click artifacts** such as the AbstractAssistant
   `.app` and any future launcher. The bootstrap and the packages it installs need no signature of
   ours.

## Consequences

- Users on all three OSes get one command and a browser console instead of waiting for signed
  installers.
- Users must paste a command into a terminal. Enterprise channels (MSI, pkg, offline bundles)
  remain future work and are out of scope for this decision.
- Service registration and first-run sign-in depend on gateway features (`service`,
  `claim-url`). With gateways that lack them the install still works, but the gateway does not
  start at login (macOS, Linux) and the user signs in with the admin token file.
- Scripts that pipe vendor installers inherit the vendors' behavior (for example, Ollama's Linux
  installer uses sudo and creates a system service). The scripts make those steps opt-in.
- Windows is covered by CI smoke tests only until it is validated on real machines.

## Enforcement

- `docs/installers/strategy.md`, `security-and-os-blocks.md`, `user-journeys.md`,
  `components.md` and `implementation-plan.md` describe this model; changes that reintroduce a GUI
  installer manager need a new ADR that supersedes this one.
- The bootstrap scripts must not install machine-wide state except through an opt-in vendor
  installer the user asked for, and must keep `--print`/`-Print` side-effect free.
- New bootstrap steps must print their command and appear in the summary's "same steps by hand".

## Validation

- `python -m pytest -q` (root): manifest schema v2, `bootstrap` and console-first `post_install`,
  script pins equal to the manifest, `install.sh --print` installs nothing, doctor probes.
- `bash scripts/tests/test_inventory.sh`: `install.sh`/`install.ps1` pins equal the manifest and
  the root gateway pin.
- CI job `bootstrap-smoke` (ubuntu, macOS, Windows): dry run, real install of the published pin
  with `--no-service --no-open --port 18080 --profile light`, `/api/health`, re-run, uninstall.
