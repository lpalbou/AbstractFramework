# Admin-initiated token reset without admin visibility: comparative analysis

Governance backlog evidence, 2026-10-15. Question: an admin must be able to invalidate or regenerate a user's bearer token but never obtain it; email is optional; some users have none.

## 1. Comparison

| System | What the admin sees | Reaches the user (email / no email) | TTL, single use | Audit | Failure mode prevented |
|---|---|---|---|---|---|
| **Vault response wrapping** [1][2][3] | A *wrapping token* only: "not the actual secret but a reference" [1]. | Any channel; recipient unwraps. AppRole: RoleID and SecretID "through two different channels", SecretID wrapped, `secret_id_num_uses=1` [3]. | Single-use, own short TTL; `lookup` "tells you if the token has already been unwrapped or is expired" [1]. | "A client receiving a token that cannot be unwrapped can trigger an immediate security incident" [2]. | Interception or replay by an intermediary. |
| **Vault root tokens** [4][5][6] | `generate-root` output is XORed with an OTP or PGP-encrypted: only the holder decodes it [6]; root "revoked immediately after" setup [4]; accessors revoke "not including the actual token ID" [4]; `num_uses` gives "a one-time-token" [5]. | Hand-carried. | Quorum, OTP, use count. | Accessor lookups. | A standing shared root secret. |
| **GitHub PATs** [7][8][9][10] | Creator sees it once: "you will not be able to see the token again" [7]. Org owners see name, owner, permissions and can revoke; never the value [9]. | Users self-issue; admins never issue. Lifetime capped by policy [8]. | Expiry mandatory; revocation immediate [10]. | Revocations "recorded in the audit log" + email to the creator [9][10]. | Admin exfiltration; silent revocation. |
| **GitLab** [11][12][13][14] | PAT: "you cannot view it again" [11]. Admins MAY mint PATs and *impersonation tokens* for any user and receive the value once [12]; impersonation can be disabled instance-wide [13]. | Admin hands it over (trade-off: admin sees it). | ≤365 days by default [11]. | `personal_access_token_created/revoked`, `user_impersonation` [14]. | Audited convenience. |
| **Keycloak** [15][16] | A Temporary password the admin typed ("the user must change the password at the first login") or nothing [15]. | Email: Credential Reset link, required action Update Password, "you can set the validity of the email link" [15]; API `execute-actions-email?lifespan=` [16]. No email: temporary password. | Link lifespan configurable; forced change. | Admin events. | Standing admin-known password. |
| **Okta** [17][18][19] | Reset email ("The link expires in one hour") or temporary password: account "marked as expired", "must change their password upon signing in"; "Sign out user" [17]. Admin sees the temporary password [18]. | No email: API `activate?sendEmail=false` "returns an activation link" the admin delivers by any channel [19]. | 1 h link; password dies at first use. | System log. | Long-lived links; sessions surviving a reset. |
| **Auth0** [20][21][22] | A URL, never the credential: password-change ticket (`ttl_sec` default 5 days) [20]; invitation with `send_invitation_email=false` returns `invitation_url` (7 days default, 30 max) [21]. | Email by default; otherwise the admin forwards the URL. Passwordless needs email/phone [22]. | Per-ticket TTL. | Tenant logs. | Secret transiting a human. |
| **Microsoft Entra** [23][24] | Reset: autogenerated temporary password, "give it to the user", must change at next sign-in, but it "never expires" [23]. Temporary Access Pass: "time-limited passcode", single- or multi-use, default 1 h, max 30 days; "You can't view this value after you select Ok"; Global Readers see details "without reading the code itself"; admins create for others "(except themselves)"; one TAP per user, new overrides [24]. | TAP is the no-email path. | One-time option; hard expiry; replacement invalidates. | Sign-in/audit logs. | Admin-set permanent password; recovery without any method. |
| **AWS IAM** [25][26][27] | Access keys "can be retrieved only at the time you create it"; "IAM users with access keys are an account security risk" [25]. Console: autogenerated password + "User must create a new password at next sign-in (recommended)" [27]. | Admin hands it over (sees it). AWS's answer: federation with "temporary credentials", IAM Identity Center [26]. | Keys are long-term (the anti-pattern). | CloudTrail. | Names the anti-pattern itself. |
| **Kubernetes** [28][29][30][31] | Bootstrap token `id.secret`, admin sees it but it can only join [28]. TokenRequest: short-lived, audience/object-bound; Secret tokens "not recommended" [30]. | Hand-carried; `kubectl create token --duration 10m` [31]. | 24 h default TTL; `tokencleaner`; "discouraged to share the same token" [28][29]. | API audit. | Long-lived, broad bootstrap secrets. |
| **Tailscale auth keys** [32][33] | Admin generates and sees the key. One-off keys usable "one time", auto-revoked after use; reusable keys "very dangerous if stolen" [32]. | Hand-carried. | 1–90 days; tags bind identity [32]. | "Create API key", "Revoke API key", "API key expired" with actor [33]. | Replay of a stolen enrolment key. |
| **SSH certificates** [34][35] | Nothing secret: user keeps the private key; CA signs the public key with key id "used in logs and may be used to revoke keys", principals, validity [34]; Vault example `ttl: 30m` [35]. | Public key in, certificate out. | Short validity; KRL revocation. | Key id in logs. | Any secret handover. |
| **NIST SP 800-63B/63A rev 4** [36][37] | Record of all bound authenticators (4.1); binding code "usable only once ... maximum of 10 minutes" or ≥112 bits, "SHALL NOT be communicated over any insecure channel (e.g., email)" (4.1.2.2); binding/recovery "SHALL cause a notification" via an independent channel (4.1.2.1, 4.2); passwords "salted and hashed" (3.1.1.2); look-up secrets used once (3.1.2.2); expired "SHALL NOT be usable" (4.4). 63A 3.8: confirmation codes ≥6 digits, invalidated on use, ≤10 min phone, 24 h email, 21–30 days postal. | | | | |
| **OWASP** [38][39] | Reset tokens: CSPRNG, long, "Single use and expire", stored like passwords, rate-limited; consistent messages for existent and non-existent accounts; "do not send the password in the email!"; side-channel PIN then "a limited session" that only permits reset [38]; generic login errors, log failures [39]. | | | | |
| **RFC 8628 Device Grant** [40] | For devices lacking a browser: `device_code` + `user_code`; device shows code and `verification_uri`; user approves elsewhere; `expires_in`; "rate-limit user code attempts"; code "sufficiently short to limit ... phishing". | No email: the *user* claims on the device, approval happens elsewhere. | Short-lived. | | Typing secrets on constrained devices. |

Pattern: nobody but the holder sees a long-lived credential. Systems (a) issue a short-lived, single-use *reference* the holder exchanges (Vault, Keycloak/Okta/Auth0 links, Entra TAP, Kubernetes, Tailscale), (b) sign a holder-generated key (SSH certificates), or (c) tolerate admin visibility only for a secret that dies at first use, audited loudly (temporary passwords, GitLab impersonation).

## 2. Recommendation for AbstractGateway

**A one-time, short-TTL claim code, exchanged for the real token at first sign-in.**

1. **Issue.** `POST /admin/accounts/{id}/credential/reset` revokes the current token (NIST 4.3 [36]) and creates a *claim code*: ≥128 bits from a CSPRNG for links; if a typable form is offered, ≥8 characters, strict rate limit, ≤10 min TTL (NIST 4.1.2.2 [36]; Entra [24]). Store only its hash with account, `expires_at`, `issued_by`. Default TTL 1 h, max 24 h (63A 3.8 [37]); one outstanding code per account, re-issue invalidates the previous [24].
2. **Deliver.** If SMTP is configured and the account has an email, the gateway mails the claim link and the admin sees nothing [16][17]. Otherwise the gateway shows the code **once** to the admin ("You can't view this value after you select Ok" [24]) who hands it over by any channel. Third option: the user's client displays a short code and the admin approves it in the admin UI (RFC 8628 [40]); the admin never holds anything claimable.
3. **Claim.** `POST /auth/claim {code}`: constant-time hash check, unexpired, unused; record `claimed_at`, `claimed_from`; mint the bearer token, return it once, store only its hash [36][38]. The admin API has no read path for token values, only ids for revoke [4][9]. Optionally force a password or passkey in the same session [15][27]. Generic errors, per-account rate limit, no enumeration [38][39].
4. **Revoke/regenerate.** `DELETE .../credential` revokes by id and ends sessions [17]; it may issue a new claim code in the same call.
5. **Audit.** Append-only: `credential.reset_requested` (actor, account, mode, TTL), `credential.claim_delivered` (email | shown-to-admin | device), `credential.claimed` (at, from), `credential.claim_failed`, `credential.claim_expired`, `credential.revoked`. Notify the user through any independent channel (NIST 4.1.2.1, 4.2 [36]) and show "claimed at/from" on the user's account page.
6. **Digital users and automation.** An entity runtime is a client like any other: its creator receives a claim code and passes it to the runtime at first start by flag; the runtime claims, stores the token in its own sealed credential file, and the code dies [3][28][32]. Showing a bootstrap token once to the creator (GitHub/GitLab/AWS style) is acceptable only when creator and operator are the same person; otherwise it is the access-key anti-pattern [25][26]. Scripts should prefer short-TTL scoped tokens requested at run time [30][31]; rotation = revoke + new claim code to the script's owner.

**Residual risk.** An admin holding the claim code can claim it first and impersonate the user until detected; email and the device-style flow remove this, hand-over does not. Mitigations: single use plus short TTL keeps the window small and makes the user's own failed claim a loud signal ("an immediate security incident" [2]); `claimed_at/from` shown to the user and logged makes it attributable; re-issue invalidates, so recourse is one click; admins cannot reset their own credential and read-only admins see metadata, never codes [24]. What remains equals GitLab impersonation: an audited, visible admin act, not a silent one [13][14].
